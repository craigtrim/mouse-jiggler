# Acceptance record, version 1.0.0

**Status: partially executed on one machine.** The 1.0.0 release is still blocked.

Some rows now carry real results, taken on Windows 10 Pro build 19045 x64, which is one of the OS
rows the matrix requires. Two kinds of row have been executed: the performance gates, which have
numbers, and the functional rows that need no hardware this machine lacks and no unattended input
injection, which ran against the real packaged artifacts through `scripts/verify-acceptance.ps1`
and `scripts/verify-lifecycle.ps1`. Both sets are listed below.

Every other row is **not run**, and the reasons are given rather than left implied.

Nothing here was run on a dedicated acceptance machine, and no row involving unattended input
injection was run at all: the epic is explicit that it must not happen on a working desktop, and
this was a working desktop. A row that says passed says so because it was executed, not because
it seemed likely.

## What the matrix still needs

The remaining rows in [issue #14](https://github.com/craigtrim/mouse-jiggler/issues/14) need
hardware and environments that one development machine cannot stand in for:

- Windows 10 22H2, Windows 11 24H2 and Windows 11 25H2, plus a smoke pass on Windows 11 build 22000.
- A physical laptop for real AC and battery transitions, lid close and resume.
- A desktop with no battery, to exercise power detection where there is nothing to report.
- Two monitors with negative coordinates and mixed DPI, and an undocking case.
- A screen reader, High Contrast, and 100/150/200% display scaling with 150% text.
- A dedicated desktop for unattended input injection, which must not be someone's working machine.
- A second signed-in Windows session, to reach the uninstaller's cross-session branch. The mutex
  and the pipe are both per session, so a copy running under another account cannot be asked to
  close; only the refusal path is reachable there, and it needs a real second session to see.

Marking those as passed on the strength of one machine would be a false claim, so they stay
**not run**.

## Rows executed on this development machine

`scripts/verify-acceptance.ps1` runs the rows of the matrix that need no hardware this machine
lacks and no unattended input injection. They were previously listed as **not run** alongside
rows that genuinely cannot be executed here, which understated what is known: a row that can be
run and has not been is a different thing from a row that cannot be run at all.

Every check below ran against the real packaged artifacts, using real processes, the real
installer and the real `%LOCALAPPDATA%\MouseJiggler` directory. Nothing was simulated, and
nothing here touches the pointer.

| ID | Check | Result |
| --- | --- | --- |
| A19a | The first copy runs and owns the session | Passed |
| A19b | A duplicate `--startup` launch exits quietly rather than starting a second engine | Passed |
| A19c | A copy at another path does not start a second engine either | Passed |
| A19d | Exactly one engine process remains, and it is the original | Passed |
| A25a | A running app opens no TCP or UDP socket, sampled over six seconds | Passed |
| A21a | A truncated `settings.json` does not crash the app | Passed |
| A21b | The damaged file is left byte for byte as it was | Passed |
| A21c | Nothing is quarantined without an explicit Reset settings | Passed |
| A21d | No backup is written over a file that was never successfully read | Passed |
| A23a | A fresh install writes exactly one startup entry | Passed |
| A23b | An upgrade leaves a `StartupApproved` disabled decision untouched | Passed |
| A23c | An upgrade does not rewrite the Run value | Passed |
| A23d | An ordinary launch leaves the disabled decision untouched | Passed |

A23b and A23d plant the undocumented `StartupApproved` bytes that Windows writes when a user
switches the app off in Settings or Task Manager. The application must never write them, which is
precisely why a test has to: there is no supported way to ask Windows whether startup is enabled,
so the only way to show the app respects the answer is to set it and watch nothing undo it.

`scripts/verify-lifecycle.ps1` covers the rest of what two processes can establish here: a
portable copy adopted by an installation without losing its settings, an upgrade over a running
copy, an ownership conflict refused with exit code 3 while the target keeps running, uninstall
removing only what it owns, and a silent uninstall keeping the shared settings.
